# 视觉信息注入文档

本文整理当前 ClawNav + OpenClaw 视觉注入方案，覆盖运行入口、代码路径、trace 证据、当前验证结果和已知边界。这里的“视觉注入”不是把 PIL/raw image 直接作为多模态消息塞进 OpenClaw agent，而是把 Habitat RGB frame 保存为本地图片路径，再由 ClawNav `/plan` adapter 可选调用 OpenClaw 图像描述能力，把结构化文字观察注入 planner prompt、memory write、memory recall 和 JanusVLN policy prompt。

## 总体方案

当前链路分三层：

```text
Habitat RGB frame
  -> 保存到 OUTPUT_PATH 下的 keyframes / openclaw_current_frames
  -> current_image_path / recent_keyframe_paths / keyframe_candidate 进入 /plan payload
  -> OpenClaw CLI adapter 可选执行 image describe-many
  -> visual_observations 回到 planner runtime_metadata
  -> runtime 自动写入 SpatialMemory 并召回 episode-local memory
  -> JanusVLN NavigationPolicySkill 使用短 memory_context_text 继续决策
```

关键设计边界：

1. 路径注入：始终传 `current_image_path`、`recent_keyframe_paths`、`keyframe_candidate.image_path`。
2. 描述注入：只有 `/plan` adapter 以 `OPENCLAW_VISUAL_MODE=describe` 启动时才调用 OpenClaw/Qwen 图像描述。
3. 记忆注入：真实长期视觉记忆需要 `HARNESS_MEMORY_BACKEND=spatial_http`，否则默认 `fake` backend 只能做 smoke。
4. 动作边界：OpenClaw planner 的 `arguments.action_text` 默认不覆盖 JanusVLN policy；runtime 只记录 `planner_action_guidance`。只有显式传 `--openclaw_allow_planner_action_override` 才允许跳过 policy。
5. Prompt 控制：OpenClaw 视觉 memory 注入 policy 前会被压缩成短导航证据，避免长 markdown、模型过程文本或动作级 guidance 污染 JanusVLN 指令。

## 运行入口

### 通用 30 episode gateway 评测

`scripts/evaluation_openclaw_gateway.sh` 是通用入口。它负责启动 JanusVLN 评测，把 harness 切到 OpenClaw runtime：

```bash
--harness_runtime openclaw_bridge
--harness_mode memory_recall
--harness_memory_backend "${HARNESS_MEMORY_BACKEND}"
--harness_memory_source "${HARNESS_MEMORY_SOURCE}"
--openclaw_planner_backend gateway
--openclaw_gateway_url "${OPENCLAW_GATEWAY_URL}"
```

当前脚本包含几个防误跑保护：

- 固定 30 个 `scene_id:episode_id` 作为默认 `HARNESS_EPISODE_KEYS`。
- `MAX_STEPS` 必须是正整数，避免再次产生 `MAX_STEPS=0` 的一跳全 0 结果。
- 默认 `CHECK_GATEWAY=1`，并且 `REQUIRE_OPENCLAW_CLI_ADAPTER=1` 时会要求 `/health.service == openclaw_cli_plan_gateway`，避免连到 simple gateway。
- `OPENCLAW_SERVICE_REGISTRY` 可以显式置空，避免过期 SERVICE.md 覆盖 `SPATIAL_MEMORY_URL`。

这个脚本默认：

```bash
HARNESS_MEMORY_BACKEND=${HARNESS_MEMORY_BACKEND:-fake}
HARNESS_MEMORY_SOURCE=${HARNESS_MEMORY_SOURCE:-episode-local}
```

因此它默认不能证明真实 SpatialMemory 写入/召回质量。

### 视觉记忆评测入口

`scripts/evaluation_openclaw_visual_memory.sh` 是当前更接近目标方案的入口。它在调用通用 gateway 评测前设置：

```bash
OPENCLAW_VISUAL_MODE=describe
OPENCLAW_VISUAL_MODEL=qwen/qwen3.5-flash
OPENCLAW_VISUAL_MAX_IMAGES=2
HARNESS_MEMORY_BACKEND=spatial_http
HARNESS_MEMORY_SOURCE=episode-local
OPENCLAW_ENABLE_SUBAGENT_CRITIC=1
OPENCLAW_ENABLE_SUBAGENT_MEMORY_CURATOR=1
REQUIRE_GATEWAY=1
REQUIRE_OPENCLAW_CLI_ADAPTER=1
```

它还会先跑 `scripts/check_openclaw_visual_plan_gateway.py`。这个 preflight 会验证：

- `/health` 是 `openclaw_cli_plan_gateway`，不是 simple gateway。
- OpenClaw image capability 能返回非空 `visual_observation` 或 `caption`。
- `/plan` response 有 `runtime_metadata.visual_analysis.ran=true`。

## Adapter 启动方式

ClawNav `/plan` adapter 由 `scripts/start_openclaw_cli_plan_gateway.sh` 启动：

```bash
HOST=127.0.0.1 \
PORT=8011 \
OPENCLAW_PLANNER_MODE=agent \
OPENCLAW_VISUAL_MODE=describe \
OPENCLAW_VISUAL_MODEL=qwen/qwen3.5-flash \
OPENCLAW_VISUAL_MAX_IMAGES=2 \
OPENCLAW_VISUAL_INTERVAL_STEPS=10 \
OPENCLAW_VISUAL_TIMEOUT_MS=90000 \
OPENCLAW_AGENT_TIMEOUT=180 \
./scripts/start_openclaw_cli_plan_gateway.sh
```

默认 `OPENCLAW_VISUAL_MODE=path`，只传图片路径，不调用图像描述。要证明视觉内容进入 planner，必须使用 `describe`。

`OPENCLAW_VISUAL_INTERVAL_STEPS` 控制 describe 频率：

- `1`：每步都做 VLM describe，证据最密，但非常慢。
- `10`：关键帧/间隔式 describe，更适合长评测。
- 无论 interval 如何，`keyframe_candidate.image_path` 存在时会优先触发视觉分析。

## 每步图片如何保存

代码入口在 `src/evaluation_harness.py` 的 `HarnessModelProxy.call_model()` 和 `_runtime_payload()`。

每个 step 会从 JanusVLN 当前 `images` 中取最后一帧：

```text
images[-1] -> current frame
```

保存规则：

- `WorkingMemory.should_promote_keyframe(step_id)` 为真时保存到 keyframe。
- 否则保存为普通 current frame。
- 默认 keyframe 规则是 step 0 和每 10 step：

```python
return step_id == 0 or (interval > 0 and step_id % interval == 0)
```

输出路径大致是：

```text
<OUTPUT_PATH>/keyframes/<scene_id>/<episode_id>/step_000000.png
<OUTPUT_PATH>/openclaw_current_frames/<scene_id>/<episode_id>/step_000001.png
```

runtime payload 会带上：

```json
{
  "policy_action": "MOVE_FORWARD",
  "run_id": "<OUTPUT_PATH>",
  "current_image_path": ".../step_000010.png",
  "recent_keyframe_paths": [".../step_000000.png", ".../step_000010.png"],
  "keyframe_candidate": {
    "step_id": 10,
    "reason": "interval",
    "has_current_image": true,
    "image_path": ".../step_000010.png"
  }
}
```

`run_id` 当前取 `OUTPUT_PATH`，用于区分同一 adapter 生命周期内重复跑同一 scene/episode/step 的 OpenClaw agent session。

## /plan payload 如何压缩

`src/harness/openclaw/openclaw_cli_plan_gateway.py` 的 `OpenClawCliPlanPlanner._prompt_payload()` 会把 `/plan` payload 压缩后再交给 OpenClaw agent。

保留的 state 字段：

```text
scene_id
episode_id
instruction
step_id
last_action
```

保留的 runtime context 字段：

```text
run_id
policy_action
current_image_path
recent_keyframe_paths
memory_context_text
memory_images
keyframe_candidate
visual_observations
```

限制策略：

- `recent_keyframe_paths` 只保留最近 2 个。
- `memory_context_text` 最多 300 字符进入 OpenClaw planner prompt。
- `memory_images` 最多 2 张进入 OpenClaw planner prompt。
- `visual_observations` 只在 `OPENCLAW_VISUAL_MODE=describe` 且通过 interval 判断时生成。

这样做的目标是让 OpenClaw planner 能看到必要视觉/记忆上下文，但不把完整历史图像和长 memory 文本塞进 prompt。

## OpenClaw 图像描述如何进入 planner

当 adapter 使用 `OPENCLAW_VISUAL_MODE=describe` 时，`OpenClawVisualAnalyzer` 会执行：

```bash
openclaw capability image describe-many \
  --file <current_image_path> \
  --file <recent_keyframe_path> \
  --prompt "<navigation visual prompt>" \
  --json \
  --timeout-ms <timeout>
```

返回结果会被规范化为类似结构：

```json
{
  "image_path": "...",
  "caption": "...",
  "visual_observation": "...",
  "landmarks": [],
  "objects": [],
  "spatial_cues": [],
  "navigation_relevance": "...",
  "confidence": 0.8,
  "analysis_metadata": {
    "vlm_latency_ms": 1234.5,
    "visual_model": "qwen/qwen3.5-flash",
    "visual_mode": "describe",
    "cache_hit": false,
    "error": false
  }
}
```

adapter 会把这些 observation 放入：

```text
prompt_payload.runtime_context.visual_observations
decision.runtime_metadata.visual_analysis
```

trace 中对应字段是：

```text
visual_analysis.ran
visual_analysis.num_images
visual_analysis.image_paths
visual_analysis.vlm_latency_ms
visual_analysis.cache_hits
visual_analysis.failures
visual_analysis.model
visual_analysis.observations
```

## 长期视觉记忆写入

当前有两条写入路径。

### Planner 显式写入

OpenClaw planner 可以返回：

```json
{
  "intent": "write_memory",
  "tool_name": "MemoryWriteSkill",
  "arguments": {
    "image_path": "...",
    "write_gate": {
      "candidate_reason": "planner_request",
      "curator_decision": "write"
    }
  }
}
```

`OpenClawVLNRuntime._memory_write_arguments()` 会用 `keyframe_candidate`、`current_image_path` 和匹配的 `visual_observations` 补全：

```text
caption
visual_observation
objects
landmarks
place_category
spatial_cues
navigation_relevance
confidence
write_gate
write_type=episodic_keyframe
```

### 自动视觉写入

即使 planner 没有显式返回 `write_memory`，只要本步 `visual_analysis.ran=true` 且有匹配 observation，runtime 会走自动写入：

```text
OpenClaw visual_analysis.observations
  -> _auto_write_visual_memory()
  -> VisualMemoryCuratorSkill
  -> MemoryWriteSkill
  -> _remember_written_visual_memory()
```

自动写入默认：

```text
memory_source=episode-local
candidate_reason=openclaw_visual_analysis
write_type=episodic_keyframe
```

写入成功后，runtime 会把最近写入的 visual memory 缓存在 `recent_visual_memories`，最多保留 10 条，用于后续自动召回判断。

trace 中应看到：

```text
tool_calls[].tool_name=VisualMemoryCuratorSkill
tool_calls[].tool_name=MemoryWriteSkill
memory_writes[].written=true
memory_writes[].image_path
memory_writes[].memory_scope
memory_writes[].memory_namespace
memory_writes[].write_gate
```

## 长期视觉记忆召回

召回由 `MemoryQuerySkill` -> `MemoryManager.recall()` -> spatial memory client 完成。

runtime 默认把查询限制在当前 episode：

```python
allowed_scopes = ["episode"]
memory_namespace = f"episode:{scene_id}:{episode_id}"
```

这避免当前 episode 误召回其他 episode 或未来信息。

当前也有两条召回路径：

1. Planner 显式返回 `intent=recall_memory`。
2. runtime 在已经有 `recent_visual_memories` 时自动做 pre-planner 或 after-write recall。

召回结果分三类上下文：

```text
policy_context: 给 JanusVLN NavigationPolicySkill
control_context: 给 critic / runtime 判断
executor_context: 给 executor / anchor
```

policy 侧只使用：

```text
memory_context_text
```

当前 runtime 多处调用 `_merge_tool_navigation_context(..., include_memory_images=False)`，也就是默认不把 `memory_images` 传给 JanusVLN policy。这样可以避免把外部 memory image 当成额外 JanusVLN image history，引起输入张量/语义混乱。`memory_images` 仍会保留在 recall 记录里，供 trace 和后续 ablation 使用。

trace 中应看到：

```text
recall_usage[].event_type=memory_recall
recall_usage[].selected_namespace=episode:<scene_id>:<episode_id>
recall_usage[].num_hits
recall_usage[].hit_image_paths
recall_usage[].used_by_policy
recall_usage[].used_by_planner
recall_usage[].action_changed_after_recall
```

## Policy memory prompt 如何压缩

`src/harness/memory/memory_manager.py` 负责把 memory hits 转成 JanusVLN policy prompt。

当前保护逻辑：

- 每条 memory evidence 最多保留 2 个片段。
- 每条 evidence 最多 180 字符。
- 总 `memory_context_text` 受 `max_prompt_context_chars` 限制，默认 1200。
- 优先保留带导航词的片段，如 `archway`、`corridor`、`doorway`、`forward`、`left`、`right`、`path`。
- 过滤模型过程文本和泛化 heading，例如：
  - `the user wants`
  - `i need to`
  - `drafting the description`
  - `based on the visual evidence`
  - `here is a description`

policy prompt 最终形态应接近：

```text
Relevant memory:
- semantic_frame: Large plaster archway on the left leads into the kitchen; path continues forward through doorway (confidence=0.54)
```

而不是整段 markdown 视觉描述或 OpenClaw agent 的推理过程。

## Planner action 与 JanusVLN action 的边界

OpenClaw planner 可以返回 `arguments.action_text`，但当前默认不让它直接接管环境动作。

代码路径：

```text
src/evaluation_harness.py
  --openclaw_allow_planner_action_override 默认 False

src/harness/config.py
  openclaw_allow_planner_action_override=False

src/harness/openclaw/runtime.py
  planned_action_text && allow_planner_action_override
    -> policy_skipped=true, action 由 OpenClaw 接管
  planned_action_text && !allow_planner_action_override
    -> planner_action_guidance 只写 metadata
    -> NavigationPolicySkill 仍然被调用
```

当前推荐默认是不 override。原因是前面实测发现动作级 guidance 写进 JanusVLN `Current subgoal` 会干扰 baseline policy，尤其当 OpenClaw 建议 `STOP` 或与 JanusVLN 局部视觉动作相反时。现在 OpenClaw 更适合作为视觉/记忆信息提供者，而不是替代低层离散动作策略。

## Agent session 隔离

OpenClaw CLI adapter 的 session id 由以下字段组成：

```text
agent_session_id
scene_id
MMDDHHMM
```

对应代码是 `OpenClawCliPlanPlanner._agent_session_id_for_payload()`。

默认 `agent_session_id=clawnav`，所以 OpenClaw 侧看到的显式会话 key 形如：

```text
explicit:clawnav-<scene_id>-<MMDDHHMM>
```

例如 5 月 22 日 10:40 在 `zsNo4HB9uLZ` scene 下运行时，会话名类似：

```text
explicit:clawnav-zsNo4HB9uLZ-05221040
```

这样可以把同一 scene、同一分钟内的 episode/step 聚合到一个 OpenClaw 对话中，避免之前按 run/episode/step 生成大量碎片会话，例如 `explicit:clawnav-...-zsNo4HB9uLZ-251-8`。

## 如何判断视觉真的参与了

不要只看图片是否保存。保存图片只能证明 harness 有 frame artifact，不能证明 OpenClaw 看到了视觉内容。

先跑汇总：

```bash
python scripts/summarize_openclaw_vln_ablation.py <OUTPUT_PATH>
```

视觉 gateway 活跃的最低证据：

```text
invalid_run_reason == ""
all_episodes_one_step == false
planner_backend == gateway
planner_fallback == false
oracle_leakage_steps == 0
image_paths_used present
visual_analysis_steps > 0
visual_analysis_failures == 0 或很低
```

长期视觉记忆真正参与的证据：

```text
memory_write_attempts > 0
memory_write_written > 0
memory_recall_events > 0
recall_events_with_hits > 0
useful_recall_rate > 0
memory_scope_counts 中有 episode
memory_namespace_counts 使用 episode:<scene_id>:<episode_id>
```

trace 级别应检查：

```text
visual_analysis.ran=true
visual_analysis.observations 非空
memory_writes[].written=true
recall_usage[].used_by_policy=true
tool_calls 包含 MemoryWriteSkill / MemoryQuerySkill
policy_skipped 不是默认出现
planner_action_guidance 只在 metadata 中，不应变成 Current subgoal 污染 policy
```

## 当前结果解读

截至目前已有两类结果，含义不同：

1. `results/clawnav_openclaw_gateway_30_fixed_fast_codex_20260521`
   - `success=0.8667`
   - `SPL=0.8230`
   - `length=30`
   - `invalid_run_reason=""`
   - 证明 `MAX_STEPS=400` 后 30 episode 评测不再是一跳全 0。
   - 但该 run 的 `visual_analysis_steps=0`，不能作为 visual-memory 正收益证据。

2. `results/clawnav_openclaw_visual_memory_regressions4_compact_20260521`
   - `visual_analysis_steps=38`
   - `memory_write_written=38`
   - `memory_recall_events=405`
   - `success=0.0`
   - 证明 visual memory 链路确实跑通，但旧代码下动作级 guidance / memory prompt 污染仍导致 4 个退化 episode 全失败。

因此当前结论是：

```text
评测链路 bug 已修；
视觉描述、写入、召回链路已打通；
visual-memory 对 SR/SPL 的正向收益还没有被完整 30 episode 干净对比证明。
```

## 当前设计的局限

1. OpenClaw planner 仍不是 raw image 多模态 agent；它主要消费图片路径和 describe 后的文字观察。
2. `OPENCLAW_VISUAL_MODE=path` 只能证明路径传递，不能证明图像内容被理解。
3. 每步 VLM describe 很慢，长评测需要 `OPENCLAW_VISUAL_INTERVAL_STEPS` 控制频率。
4. 真实长期记忆依赖外部 SpatialMemory 服务，端口、data dir、SERVICE.md registry 都可能污染实验。
5. 当前 policy 默认不消费 `memory_images`，只消费压缩后的 `memory_context_text`。
6. OpenClaw action guidance 当前只应作为 metadata；直接注入 active subgoal 或覆盖 action 容易伤害 JanusVLN 局部策略。
7. 关键帧选择仍主要是固定间隔，不是基于视觉变化或语义新颖度。

## 后续可改进方向

1. 做严格 A/B：baseline/simple gateway、describe-only、describe+spatial memory，统一 30 episode 和 `MAX_STEPS=400`。
2. 把关键帧提升从固定 10 step 改成视觉变化、新 landmark、新 spatial cue 或 planner uncertainty 触发。
3. 给 `MemoryWriteSkill` 增加更强 novelty/duplicate gate，减少相似关键帧重复写入。
4. 单独做 `memory_images` ablation，区分“文字 memory 进入 policy”和“图像 memory 进入 policy”的影响。
5. 在 trace 里更明确记录每次 policy prompt 最终收到的 compact memory 文本，方便定位 prompt 污染。
6. 把 OpenClaw planner guidance 分层：只允许高层 replan subgoal 进入 policy，普通离散 action 只保留 metadata。
